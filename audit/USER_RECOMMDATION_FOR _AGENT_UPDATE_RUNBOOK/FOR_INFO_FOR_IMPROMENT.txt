Architecting the Secure CI/CD Bridge: GitHub to Google Cloud
To implement the rigorous automation plan detailed above, and to successfully deploy updates that result in the specific .a.run.app dashboard provided by the user, a highly secure integration between GitHub and Google Cloud must be established. Historically, this integration relied on exporting long-lived Service Account Keys (JSON files) from Google Cloud and storing them as repository secrets in GitHub.
This legacy approach introduces catastrophic security risks. If a Service Account Key is exfiltrated by a malicious actor, accidentally printed in build logs, or stolen via a supply chain attack on a third-party GitHub Action, the attacker gains persistent administrative access to the Google Cloud environment. Such a breach could easily bypass the "fail-closed" safety boundaries mandated by the Genesis_System3 plan, allowing unauthorized actors to alter the deployment, expose broker tokens, or manipulate live trading parameters.
To strictly adhere to the safety boundaries—which explicitly prohibit unnecessary secret payload exposure (as seen in Issue #228)—the modern deployment architecture must utilize Workload Identity Federation (WIF). WIF eliminates the need to manage, store, or rotate long-lived service account keys. Instead, it leverages the OpenID Connect (OIDC) protocol to establish a cryptographically verifiable, ephemeral trust relationship between the GitHub repository workflow and the Google Cloud project.
