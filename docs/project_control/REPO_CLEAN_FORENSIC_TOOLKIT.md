# Genesis System3 Repo Clean Forensic Toolkit

## Permanent authority

Canonical scanner:

`python scripts/system3_repo_clean_forensic_toolkit.py --repo . --out <DIR> --github-artifacts`

Canonical workflow:

`.github/workflows/repo-clean-forensic-toolkit.yml`

This is the repository-wide cleanup authority for future agents. Do not create a second competing cleanup classifier unless this toolkit is first proven incapable of the required analysis.

## Purpose

Produce a deletion-evidence pack that lets an agent distinguish files that are safe cleanup targets from files that merely look old, duplicated, or unused. The toolkit is **report-only**. It never deletes, moves, rewrites, or quarantines repository files.

The scanner separates four different storage problems because they require different remedies:

1. **Current tracked worktree bytes** — reduced by deleting files from the current tree.
2. **Git history/object bytes** — may remain large even after a current file is deleted; history rewriting is a separate high-risk operation.
3. **GitHub Actions artifact/cache bytes** — independent of Git history and current source; use artifact/cache retention/deletion controls, not source deletion.
4. **Local ignored/untracked disk bytes** — developer/runner generated state, not necessarily GitHub repository storage.

## Deletion decision contract

### `DELETE_PROVEN_100`

The toolkit may emit this only when every machine-verifiable gate is satisfied. V1.1 permits it for:

- explicitly generated/OS/cache noise with zero detected references/importers and no protected authority signal; or
- a **non-empty**, byte-identical **non-source** duplicate in a stale/archive/backup-style path, with the same basename as a SHA-256-identical non-stale authoritative replacement, zero detected references/importers, and no protected authority signal.

The number `100` is a repository policy classification, not a mathematical claim that arbitrary dynamic software behavior can be proven impossible. The toolkit itself still performs **zero deletions**. Actual deletion occurs only in a cleanup PR.

### `REVIEW_ZERO_BYTE_MARKER`

Zero-byte files never qualify for deletion merely because all empty files have the same hash. Empty files may be semantic/package/marker files. V1.0 exposed this false-positive pattern on its first real scan; V1.1 locks it fail-closed with regression coverage.

### `QUARANTINE_FIRST_SOURCE_DUPLICATE`

A source-like file is byte-identical to another file and appears unreferenced, but source/runtime files fail closed. Do not delete directly. A cleanup PR must remove it and then pass normal mandatory CI before merge.

### `QUARANTINE_FIRST_EXACT_DUPLICATE`

A non-source file is byte-identical but the path/authority relationship is not strong enough to prove which copy is disposable. Do not delete directly.

### `QUARANTINE_FIRST_UNREFERENCED`

The file looks stale/archive/backup-like and has no detected references, but there is no SHA-256-identical authoritative replacement. Do not delete directly.

### `KEEP_REQUIRED`

Protected, runtime-sensitive, workflow/config/governance, imported, symlinked, or otherwise referenced.

## Evidence pack

The workflow uploads a short-retention artifact containing:

- `00_EXECUTIVE_DELETE_DECISION.md` — first file an agent should read.
- `01_summary.json` — machine-readable totals and confidence contract.
- `02_file_inventory.json` — every tracked file, SHA-256, size, basic authority/disposition signals.
- `03_delete_proven_100.json` — only highest-confidence deletion rows.
- `04_quarantine_first.json` — candidates that must not be directly deleted.
- `05_all_candidate_decisions.json` — full candidate decision details.
- `06_duplicate_content_groups.json` — exact SHA-256 duplicate groups and keep candidate.
- `06b_duplicate_basename_groups_review_only.json` — same-name files; never sufficient for deletion by itself.
- `07_large_current_files.json` — largest current tracked files.
- `08_python_reverse_import_graph.json` — AST-derived local Python reverse-import evidence.
- `09_git_storage_and_largest_history_blobs.json` — Git object database, full-vs-shallow history scope, and biggest visible historical blobs.
- `10_github_storage_actions_artifacts_caches.json` — repository-reported size plus paginated Actions artifact/cache storage metadata and completeness flags.
- `11_local_untracked_disk_inventory.json` — local untracked bytes.
- `12_local_ignored_disk_inventory.json` — local ignored/generated bytes.
- `DELETE_PROVEN_100_COMMANDS.txt` — commands generated only for rows already classified `DELETE_PROVEN_100`; do not run blindly.

## Full-repo scan guarantees

V1.1 scans every current tracked file for size, SHA-256, symlink state, path class, runtime/protected signals, suspicious archive/backup naming, and Python reverse importers. Deletion candidates receive additional path/basename/stem reference scanning, including workflow/Docker/package/.gitattributes critical references. Duplicate deletion proof uses content hash plus authority/path gates, never filename similarity alone.

PR mode scans every current tracked file from a shallow checkout for speed. `09_git_storage_and_largest_history_blobs.json` explicitly marks that history scope as shallow. Main/manual runs use full-history checkout and are required before any conclusion about historical Git bloat.

GitHub Actions artifact/cache pagination records API total count, inventoried count, pages scanned, and an `inventory_complete` flag. A truncated inventory must never be presented as the final storage total.

## Cleanup sequence

1. Fresh-read current `main` and active cleanup PRs.
2. Run this toolkit on the proposed/current tree.
3. Read `00_EXECUTIVE_DELETE_DECISION.md` first.
4. Require a full-history main/manual run for Git-history storage conclusions.
5. Create a cleanup PR containing only fresh `DELETE_PROVEN_100` rows you intend to remove.
6. Re-run the toolkit on the cleanup PR and verify no authority moved unexpectedly.
7. Run normal repository mandatory CI/security/safety gates.
8. For source/runtime deletion, require its separate fail-closed proof even if an older report looked safe.
9. Merge only when exact-head gates are green.
10. Re-scan `main` after merge and compare storage totals.
11. Never use source deletion to solve Git-history or Actions artifact/cache storage without proving that is the actual storage layer consuming space.

## Self-improvement rule

This toolkit is permanent and must improve rather than fork:

- Every false positive or false negative discovered during cleanup must add a regression test before the next cleanup wave.
- Never weaken a `DELETE_PROVEN_100` gate to make more files eligible.
- Add new language/import/reference/storage analyzers into this canonical toolkit as the repository evolves.
- Keep generated reports as workflow artifacts with short retention; do not grow `reports/latest/` with repeated full inventories.
- When the user asks to “clean repo”, “check duplicate files”, “free GitHub storage”, “check repo memory”, or similar, agents must start with a fresh run of this toolkit and distinguish current files vs Git history vs Actions artifacts/caches vs local disk.

## Safety

- Analyzer/PAPER only.
- `LIVE_TRADING_ENABLED=0`.
- `SYSTEM3_LIVE_TRADING_ALLOWED=0`.
- `AUTO_EXECUTE_TRADES=0`.
- No broker call, token rotation, secret payload read, order call, IAM mutation, source deletion, artifact/cache deletion, or history rewrite is performed by the scanner.
